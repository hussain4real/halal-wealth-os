# Personal Google Drive report export

M6-P4 implements a disabled integration and synthetic HTTP mocks. The owner approved exactly `drive.file`, `openid` and `email`; see [scope selection](runs/M6-P4-scope-selection.md). No real Google account, client registration, credential, consent or live export is configured. There is no production live-mode switch. Future enablement requires separate owner authorization, configuration/access review and observed account/destination tests.

## Deliberate selection

The callback exchanges a single-use, owner/session/attempt-bound state and PKCE verifier. The encrypted vault binds tokens to an owner and connection. The connected email comes from verified Google UserInfo; the app's login email and a typed destination cannot substitute. Stable OIDC `sub` and Drive owner `me`/`permissionId` occupy different identity namespaces. A newer connection start invalidates an older callback. Callback failures use no-redirect responses and remove query credentials before session previous-URL recording. Authentication, current verification and production two-factor eligibility remain required. A rejected finalization attempts token revocation; an unconfirmed cleanup is reported honestly and requires Google account-security reconciliation.

The owner can reject a school/work account before any file creation. Explicit account acknowledgement queues one empty app-created private folder; only after inspecting its actual identity, name, ownership, permissions and capabilities can the owner review a selected saved dashboard report. The review shows account, folder, saved/captured time, complete manifest, exact byte length and SHA-256; an unchecked acknowledgement admits only that reviewed content. Reviews expire after ten minutes. Delivery permission expires after one day. No Drive scanning, permissions mutation, public-link creation or arbitrary pasted destination exists.

The exported JSON is a versioned envelope containing the complete selected saved dashboard evidence, including retained source records, and a manifest. The manifest hashes the canonical payload; the receipt separately hashes the whole envelope. No live recalculation, truncation or extra financial snapshot is introduced. Only Drive admission has a 5,000,000-byte ceiling, checked before JSON decode and after final encoding. Larger saved reports remain downloadable through the existing dashboard/complete-owner paths. This report is not an operational database backup.

## Queue, retries and uncertainty

The database intent is the queue authority. `drive:tick` scans bounded current-epoch pending work; lost optional ID-only job hints do not lose the intent. One writer uses owner advisory, current user and control/operation row locks. External side-effect transactions are not automatically retried and cannot run inside caller-owned transactions. Fresh verification, connection generation, runtime epoch, actual identity, private target and content are rechecked at handoff. Credential refresh commits in a separate verified preflight before report/admission validation can fail.

A generated remote file ID is retained before create. Retries inspect that exact identity, target, app properties, size and content hash; absent provider checksum requires bounded media hashing. A 409 does not prove upload. Conflicts are never overwritten or deleted. There are at most three mutation claims. A crashed final claim becomes visibly unknown after its lease; it does not authorize a fourth create. After a delivery deadline, an earlier uncertain attempt can only inspect its existing ID and never start another mutation. Exhausted unknown outcomes require reconciliation; they are not “failed to upload.” Disconnect cannot recall a file already accepted before the stop boundary.

Exact committed request lookup precedes changed review, capacity and connection checks, and returns historical receipts without restarting work. The UI persists only owner-scoped request identities/confirmation selectors; it locks uncertain requests through reload and offers receipt lookup/exact retry. OAuth codes/tokens/verifiers, identity emails and report bodies never enter these drafts or queued jobs.

## Stop, revoke and restore

Disconnect locally stops future handoffs and rotates the generation before any remote revoke. It remains reachable by an authenticated owner whose app email lost verification, and needs no new retained receipt allocation. Revoke attempts have durable claims before network calls. Confirmed revoke erases vault material. After three unconfirmed attempts, the state remains explicitly unconfirmed, vault ciphertext is erased and the owner must revoke the app in Google account security before future live reconnect. A new connection cannot adopt another connection's token or operation.

Controls and the entire secret relation are excluded from portable owner JSON, including ciphertext. Safe connection/operation/event metadata is retained. Bounds are 16 connections and 64 operations per owner, eight fixed audit slots per subject, bounded token/identity fields and actual complete-owner-export headroom checks. No financial history is pruned. Credential failure/log text is reduced to safe fixed codes; unmatched mock HTTP and redirects fail closed.

Keep workers stopped during any future authorized restore. Configure a fresh nonsecret execution epoch outside the dump before workers start; restored connections/operations carry the old epoch and remain inspectable but held. Missing configuration also disables transport. Restoring both the database and its old runtime configuration cannot be automatically detected, so epoch rotation is an operator obligation. The encrypted operational backup includes synthetic encrypted vault state and restores all 79 catalog tables; eight reader fingerprints include Drive. APP_KEY custody remains separate from the backup encryption key. See [recovery procedure](../../ops/release/recovery.md).

## Provider contracts

Google documents [per-file scope access](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [OAuth code/refresh/revoke](https://developers.google.com/identity/protocols/oauth2/web-server), [UserInfo identity](https://developers.google.com/identity/openid-connect/reference), [pre-generated file IDs and upload retries](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [Drive User identity](https://developers.google.com/workspace/drive/api/reference/rest/v3/User) and [file metadata](https://developers.google.com/workspace/drive/api/reference/rest/v3/files). Mock evidence does not establish provider availability, real consent, live quotas or actual account permissions.

Non-authoritative post-create metadata or body responses preserve an unknown result and the retained remote identity. Transient UserInfo failures remain retryable within the existing three-claim limit; they do not invalidate an otherwise usable connection. Accepted refresh rotation is encrypted before a subsequent identity read, while every later handoff must still verify the same connected identity. Credential-stage rejection requires reconnect. An issued grant rejected for scope/type/expiry/token validation is never admitted: its bounded refresh or access credential is used for a cleanup attempt. Failed or unavailable cleanup is explicitly unconfirmed and requires Google account-security reconciliation; it is never reported as confirmed revocation.
